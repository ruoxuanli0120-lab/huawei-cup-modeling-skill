# 问题智能：先看懂题，再决定怎么建模

本文件是 UNDERSTAND 阶段（9 阶段工作流第 1 步）的方法出处。它回答一个问题：**在写任何算法之前，这道题到底是什么数学对象，最好的表示是什么。** 填写产物是 [templates/problem-audit.md](../templates/problem-audit.md)（Problem Insight Map）。

> 核心原则：**高水平数学建模的核心不是找到一个更高级的算法，而是找到一个更好的问题表示。** 一个贴合题目结构的简单模型，几乎总是优于一个与题目结构无关的复杂算法。

## 硬规则：思考顺序不可颠倒

```
问题结构(structure) → 数学抽象(abstraction) → 数学模型(model) → 求解方法(method)
（等价展开：结构 → 抽象 → 机理 → 路线 → 算法）
```

- **数学模型先从问题本身建立**（目标 + 约束 + 变量域 + 机理项），**求解方法再由模型属性决定**（连续/离散、凸/非凸、可微、整数/组合、随机、多目标、规模、预算——详见 [model-ideation.md](model-ideation.md) 的“求解方法由数学模型决定”与 Method Suitability Test）。不允许先选算法再回头给它找题意。
- **禁止 algorithm-first**：不允许“看到预测就 XGBoost、看到优化就遗传算法、看到评价就 AHP/TOPSIS/熵权、看到图就最短路”。算法是模型与路线确定后的实现选择，不是出发点。
- **禁止罗列大量模型制造复杂度**：模型的价值在契合题意，不在数量；每个候选都要指向本题的一个具体结构或难点，否则不进入锦标赛。
- 每一步都要能回答“为什么是它，而不是上一步的其它可能”。若某步跳过，必须在 Insight Map 写明跳过的理由与代价。
- 当团队已经在讨论具体算法/库/超参，却还没有写出题目的数学本质、结构与数学模型时，**立即回退到本阶段**。

## Problem Insight Map 的九个面

逐项填写（模板已给表格），每一项都必须落到**本题证据**，不写通用套话：

1. **Task（任务）**：题面到底要什么产物——是数值、决策、排序、预测、构造、证明还是解释？区分“字面要求 / 工程修复后的要求 / 二者差异”。解释类任务不自动变成优化或因果任务。
2. **Mathematical Essence（数学本质）**：剥掉行业背景后，这是什么数学问题？（如：带约束的组合优化 / 缺失数据下的条件期望估计 / 不变量下的构造 / 多目标排序 / 动力系统辨识 / 假设检验）。一句话说清，并说明为什么不是别的本质。
3. **Variables（变量）**：分清四类——**状态变量 / 决策变量 / 观测变量 / 参数**——各自的维度、单位、取值域、可见时刻。标出哪些是“题目给的”，哪些是“你引入的”。每个决策变量到底在决策什么、每个状态变量到底在描述什么，都要能一句话说清；混淆状态与决策是建模错误的常见根源。
4. **Structure（结构）**：变量之间的关系结构——线性/非线性、凸/非凸、可微/不可微、连续/离散、稀疏/稠密、静态/时序、可分/耦合。并指明有无 **时间、空间、网络、阶段（多阶段/动态规划）、随机、反馈、守恒/不变量** 结构，有无天然图/几何/概率结构。**结构决定抽象，抽象决定模型，模型决定可用的求解方法。**
5. **Difficulty（难点）**：本题真正的难点在哪（规模、不可辨识、约束冲突、信息缺失、多目标权衡、病态、随机性、证明门槛），而不是“算法不好写”。
6. **Information Structure（信息结构）**：信息何时可见、以什么粒度、有无泄漏风险、缺失机制是什么、哪些是噪声哪些是信号。预测/统计/因果题这一项决定验证划分方式。
7. **Question Dependency（小问依赖）**：见下节。
8. **Representation Alternatives（表示备选）**：若存在实质不同且合理的表示，列 2–3 个主要备选（如：原始变量 vs 对偶 vs 图/矩阵 vs 概率图 vs 生成式 vs 松弛/紧化）；若题目结构基本锁定唯一自然表示，就写明原因，不为数量制造伪备选。**好的表示会让难问题变简单**；这里是创造力真正发生的地方，交给 IDEATE 阶段展开成路线。
9. **Core Insight（核心洞察）**：优先用一句话概括本题最关键的结构性判断；若小问本质独立，可分别给出各问核心洞察，不强行捏成一个统一模型。论文只回扣真实存在的共同结构。

## 领域理论的深度：只在它改变模型结构时深入

物理、工程、通信、材料、交通、生物等专业题，先判断一件事：**领域理论会不会改变本题的模型结构？**

- **会改变模型**（机理决定了方程/约束/变量的形式）→ 建模前先弄清：关键机制、governing equations（支配方程）、变量与单位、初边值条件、守恒关系、核心假设、适用范围、主要量级（哪些项主导、哪些可忽略）、可以忽略与不能忽略的机制。再据此建立数学模型。
- **不改变建模**（领域只是背景包装，数学本质是通用的）→ **保持轻量**：写清必要假设与单位即可，**不要为显得专业而堆理论**。
- 原则：领域理论服务于“建立合适的模型”，不是论文的装饰。任何引入的机制都要落到一个具体的模型项/约束/假设，并能被验证或被数据支持；否则删掉。

## Question Dependency Graph（小问依赖图）

多问题目**必须**先画依赖图，再分头建模。目的不是强迫各问用同一模型，而是先判断哪些小问真实依赖、哪些共享对象/接口、哪些确实独立；该共享的保持一致，该独立的允许使用不同模型。

填写：
- 每个小问的**输入**来自哪里（原题数据 / 上一问输出 / 上一问的模型结构 / 共享假设）。
- 每个小问的**输出**被谁消费。
- 标出**共享的主线对象**（同一套符号、同一组变量、同一个机理、同一条故事线）。
- 明确**约束是否跨问传递**：上一问的约束/假设**不能未经判断**地带入下一问（可能更松、更紧或不再适用）。

硬要求：
- 有真实依赖/共享对象的小问应保持主线和接口一致；若各问在题意上确实独立，可以使用不同模型家族，只需说明独立性，不为形式统一牺牲贴题性。
- 上游输出被下游当作输入时，登记**接口**（单位、索引、时间口径、不确定性），下游对上游误差做传播检查（见 Hybrid playbook）。
- **Backward Projection（反向投影，一般规则）**：若后问的解包含前问的决策变量（递进式 Q1→Q2→Q3），后问完成后必须把解投影回每个前问、用前问的 Referee 重新评价；投影结果优于前问 incumbent 时，登记为前问的 projection 候选并走 晋升/淘汰 流程（淘汰必须给理由）。“前问已经做完了”**不是**忽略更优前问解的理由。机制与命令见 [run-state.md](run-state.md)（`project-back record/done`），前问进入 WRITE/DELIVER 时 gate 会核对。
- 依赖图是 route gate 的前置：依赖没理清，不允许进入 IDEATE。

## Problem-to-Model Traceability（题目语义 → 数学对象 → 关系 → 约束 → 目标）

Insight Map 回答“题目是什么数学对象”；Traceability 表把它落成**逐元素可核查的映射**，是 UNDERSTAND→IDEATE 的机器闸门（FULL/FAST 均不豁免）。模板：[../templates/traceability.json](../templates/traceability.json)；校验：`python scripts/run_state.py --project . trace check --question Q1 --file team_control/traceability-Q1.json`。

每个模型元素（变量/约束/目标/评价规则）都要回答：

| 题目元素 | 数学抽象 | 模型表达 | 在求解中的作用 |
|---|---|---|---|
| 对象 A 与 B 的依赖（题面第2段） | 图关系 | G=(V,E) | 限制合法决策顺序 |
| 资源容量限制（题面条件3） | 资源约束 | R(t) ≤ C | 判断可行性 |
| 题目要求最小化代价 | 优化目标 | min f(x) | 决定方案优劣 |

判定规则：
- **orphan = 建模风险**：任何核心变量、约束或目标若无法解释“它对应题目中的什么”，trace check 直接 FAIL——不得带着 orphan 进入求解。为了算法方便而加的变量/约束/指标，要么找到题目语义，要么删除。
- 反过来，题面中**未进入模型的条件**要列入 `unmapped_problem_conditions` 并给理由（背景介绍/冗余/已由其它约束蕴含）；遗漏硬约束是最常见的失分根因。
- 硬约束 / 软约束（偏好、评价指标）/ 输入 / 决策变量必须分 role 登记；把软约束当硬约束（或反之）会系统性扭曲模型。
- Traceability 表不一定完整出现在论文中，但 WRITE 阶段“为什么这样建”的论证直接从它取材。

## 完成的判据（UNDERSTAND → IDEATE 的闸门）

只有当下列全部成立才可进入构思路线：
- Mathematical Essence 与 Structure 已用本题证据写清，且不是从算法反推的；
- 变量已按 状态/决策/观测/参数 分清，且已从对象/关系/约束建立**数学模型雏形**（目标 + 约束 + 变量域），不是先有算法再套题意；
- **Problem-to-Model Traceability 已通过 `trace check`**（无 orphan 元素；未映射条件已列明理由）；
- 已考虑是否存在实质不同的 Representation Alternative；若存在，至少列出一个主要替代；若不存在，写清唯一性/不值得分叉的理由，不为数量制造伪表示；
- Core Insight 已清楚陈述；若小问独立，可分别陈述，不强求一句话统一全题；
- 多问题目的 Question Dependency Graph 已画出；有依赖处接口自洽，独立小问不强行串线（含需要时的 backward projection 义务登记）；
- 若领域理论改变模型结构，已写清 governing equations/单位/初边值/守恒/量级/可忽略机制；若不改变，保持轻量；
- Step 0 题面审计（退化/投机解、歧义、假设分层）已完成。
